Critical constraints

  • Unique event slug and unique owner/client-creation key.
  • Unique scan job per media record, callback nonce, and owner/route/idempotency key.
  • Explicit owner predicates plus transaction-local RLS context.
  • Supabase manages auth.users; Flyway owns application schema, keys, indexes, and policies.

Authentication sequence

Supabase handles identity; Spring validates short-lived bearer tokens.

sequenceDiagram
    autonumber
    actor Host
    participant Web as Next.js / Supabase SSR
    participant Auth as Supabase Auth
    participant API as Spring Boot API
    participant JWKS as Supabase JWKS
    participant DB as PostgreSQL + RLS
    Host->>Web: Choose Google OAuth or email/password
    Web->>Auth: Start PKCE sign-in / registration
    Auth-->>Web: Authorization code or verified session
    Web->>Auth: Exchange code with PKCE verifier
    Auth-->>Web: Access token + refresh session
    Web-->>Host: Authenticated host UI
    Host->>API: Request with Bearer access token
    API->>JWKS: Resolve/cache signing key
    JWKS-->>API: Public signing keys
    API->>API: Validate signature, issuer, expiry, audience
    API->>DB: BEGIN + transaction-local owner context
    API->>DB: Owner-scoped query under RLS
    DB-->>API: Host-owned result
    API-->>Host: Response
    alt Access token expired
        API-->>Host: 401
        Host->>Web: Ask Supabase client to refresh
        Web->>Auth: Refresh session
        Auth-->>Web: New access token
        Web-->>Host: Updated client session
        Host->>API: Retry once
    end
Spring never processes passwords, owns login callbacks, stores refresh tokens, or accepts anon/service-role tokens on host routes.
7

Draft, autosave, and publish

Optimistic concurrency, idempotency, and one authoritative transaction.

sequenceDiagram
    autonumber
    actor Host
    participant UI as Next.js editor
    participant API as Spring Boot API
    participant Idem as Idempotency service
    participant DB as PostgreSQL
    participant Telemetry as OTel exporter
    Host->>UI: Open creation form
    UI->>API: POST /events + Idempotency-Key
    API->>Idem: Claim owner + route + key + request hash
    API->>DB: Create draft and creation session
    DB-->>API: Event version 1 + session ID
    API-->>UI: 201 EventWithSession
    loop Debounced autosave
        UI->>API: PATCH event + If-Match + key
        API->>Idem: Replay or claim
        API->>DB: Owner-scoped optimistic update
        alt Current version
            DB-->>API: Incremented version
            API-->>UI: 200 saved
        else Stale version
            DB-->>API: Version conflict
            API-->>UI: 409 + current state
        end
    end
    Host->>UI: Publish
    UI->>API: POST publish + If-Match + key
    API->>DB: BEGIN + owner context
    API->>DB: Validate fields, future time, venue, media
    API->>DB: Assign slug + published_at + status
    API->>DB: Complete KPI session + product event + audit
    API->>DB: COMMIT
    API-->>UI: Canonical URL + share eligibility
    API-->>Telemetry: Export after commit and fail open
Failure leaves the event unpublished. An identical replay returns the cached response without creating a second event or transition.

Media quarantine and scanning

Direct uploads remain private until content verification succeeds.

sequenceDiagram
    autonumber
    actor Host
    participant UI as Next.js editor
    participant API as Spring Boot API
    participant Q as Quarantine storage
    participant Jobs as Scan jobs
    participant Scanner as Cloud Run ClamAV
    participant A as Active storage
    Host->>UI: Select allowed file up to 10 MiB
    UI->>API: POST media intent
    API->>API: Validate owner, role, claimed type, size
    API->>Q: Create signed upload
    API-->>UI: Media ID + upload URL
    UI->>Q: Direct private upload
    UI->>API: POST /events/{eventId}/media/{mediaId}/complete
    API->>Q: Verify object and size
    API->>Jobs: Insert unique scan job
    API-->>UI: 202 scanning
    Jobs->>API: Lease due scan job
    API->>Scanner: Signed scan request + preview-write URL
    Scanner->>Q: Short-lived download
    Scanner->>Scanner: Magic bytes + safe parse + ClamAV
    alt Clean and allowed
        Scanner->>Q: Write sanitized preview
        Scanner->>API: HMAC clean callback + object/preview digests
        API->>A: Promote verified original + preview
        API->>Q: Delete quarantine object
        UI->>API: GET /events/{eventId}/media
        API-->>UI: Active + preview status
    else Unsafe or invalid
        Scanner->>API: HMAC rejected callback
        API->>Q: Delete quarantine object
        UI->>API: GET /events/{eventId}/media
        API-->>UI: Rejected + retry guidance
    end
Callbacks are at-least-once, timestamped, nonce-protected, and idempotent. Pending or rejected attached media blocks publication.

Visibility and metadata

Public rendering cannot bypass the downstream guest-access dependency.

flowchart TD
    Request["Guest requests Next.js /e/{slug}"] --> API["Next.js calls Spring metadata API"]
    API --> Exists{"Published event exists?"}
    Exists -- No --> Missing["Neutral 404 or 410<br/>no OG metadata"]
    Exists -- Yes --> Mode{"Visibility"}
    Mode -- public --> Public["Safe metadata<br/>indexable"]
    Mode -- private_link --> Private["Safe metadata<br/>noindex"]
    Mode -- invite_only --> Blocked["Neutral unavailable<br/>sharing blocked"]
    Mode -- hidden_location --> Blocked
    Public --> Render["Render canonical /e/{slug} HTML"]
    Private --> Render
Invite-only and hidden-location modes may be configured, but they expose no public metadata until guest enforcement ships.
